# ADR-007 — Media Storage

## Status

Accepted

## Context

Studio publishes Journal and Project content to the personal website. Journal documents already support an `image` block, but the editor only accepts an externally hosted image URL. Studio needs a first-class upload path without coupling the editor to a specific storage provider.

## Decision

Use Cloudflare R2 for image binaries and Supabase Postgres for media metadata.

The architecture is:

```text
Editor → Media Service → R2
                    ↘ Supabase media_assets
```

The editor receives a `MediaAsset` URL and stores that URL in the existing image block.

## Initial constraints

- Images only.
- Maximum upload size: 10 MB.
- Supported formats: JPEG, PNG, WebP, GIF, AVIF.
- Production delivery uses `MEDIA_PUBLIC_URL` mapped to the R2 bucket.
- Uploaded objects use immutable one-year cache headers.
- The existing `image` document block remains the content-level representation.

## Why not put binaries in GitHub?

GitHub is the publication transport for structured content, not a media object store. Keeping binaries separate avoids repository growth and keeps content publication independent from asset delivery.

## Why R2?

Studio is deployed on Cloudflare and the public website is a natural consumer of static media. R2 provides object storage without internet egress charges and supports custom-domain delivery.

## Why Supabase metadata?

Studio already uses Supabase. A metadata table lets us track assets independently of documents and gives us a foundation for future reuse, cleanup, search, and media management without putting metadata into the published document itself.
